# plugin-quality-improvement 要件定義書

## 概要

- **解決する課題**: `xeiculy-plugins`が提供する既存4プラグイン（create-commit / dev-workflow / product-planner / task-planner）は、いずれも`skills`のみで構成されており、findy library（`ai/plugin`, `ai/skill`, `ai/mcp`, `ai/agentic-workflow`, `development/*`）が示すベストプラクティスとの乖離（構成要素の使い分け、CI連携、権限最小化、レビュー規約の育成、依存Issueのスタック運用等）がある。これらを解消し、個人開発で有効だった手法を将来エンタープライズ/チーム環境でも横展開できる形に整える。あわせて、個人開発を見越した新規プラグインを追加する。
- **対象ユーザー**: 主にXeicuLy自身（個人開発・日々の業務での利用）。ただし`xeiculy-plugins`はpublicリポジトリであり、他の開発者が導入・コントリビュートする可能性も考慮する。
- **参考にした類似プロダクト・事例**: findy library（`ai/plugin`, `ai/skill`, `ai/mcp`, `ai/agentic-workflow`, `development/code-review`, `development/task-breakdown`, `development/pull-request`, `development/ci-cd`, `development/notifications`, `development/release-strategy`）

## ゴール

既存4プラグインをfindy library準拠のベストプラクティスへブラッシュアップし、構成要素（commands/skills等）を適材適所で使い分けられる状態にする。あわせて、個人開発の依存タスク実装（スタックPR運用）と技術判断（ADR作成）を支援する新規プラグインを追加し、個人開発の生産性を高めつつ、将来チーム規模に展開しても通用する設計にする。

## 非機能要件

### セキュリティ

- S1: 各`SKILL.md`の`allowed-tools`は実行に必要な最小権限のみを宣言し、`rm`や`git push --force`等の破壊的コマンドは許可しない
- S2: `.mcp.json`で接続するMCPサーバーは、信頼できる提供元（公式サーバー、または自分が管理するサーバー）に限定する
- S3: CI連携を実装する場合、使用するGitHubトークンは必要最小権限のスコープに限定する（CI連携自体は今回のMUST要件外のため、実装時にのみ適用される条件付き要件）

### 保守性・拡張性

- M1: 外部コントリビューター（Issue/PR）を受け入れられるよう、プラグイン追加・変更時に確認すべき基準（ディレクトリ構成、`SKILL.md`の記述ルール等）を明文化する
- M2: 要件定義書に「今後のロードマップ」セクションを設け、今回スコープ外とした項目を将来候補として記載する

## スコープ外

- リリース自動化プラグイン（他の個人開発リポジトリへ汎用的に導入できるリリースPR自動生成・Feature Flag導入支援等）は、検討の結果不要と判断し対象外とした
- 通知プラグイン（デプロイ/CI失敗/レビュー待ちの通知支援）は、Phase 2で候補に挙がったが今回は選定されず対象外とした

## 今後のロードマップ（将来候補）

- A3: PRオープン時のCI自動セルフレビュー。将来的にCoderabbit等の外部レビューツールをやめ、Claude Codeベースのレビューに一本化する可能性がある
- 通知プラグイン: デプロイ/CI失敗/レビュー待ちなどの「気づき」を早める通知支援
- B1bのさらなる発展形（複数エージェントの動的スケジューリング等）

## 次のステップ

この要件定義書をもとに実装タスクへ分解する場合は、`task-planner:task-breakdown` スキルを起動する。
